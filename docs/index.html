Start here

Install and host your first room

Node 18 or newer. The installer symlinks the extension into ~/.omp and ~/.pi, and puts omp-link on your PATH. Nothing runs in the background afterwards.

shell
git clone https://github.com/jsbonsai/omp-link
cd omp-link
npm install && ./setup.sh
omp-link version   # 3.5.0

Then, inside an agent terminal, host a room. Nothing is shared and nobody is admitted until you approve them by hand.

~/dev/api — omp
/link create backend

Hosting room "backend" on 192.168.1.105:9900.
No peer is admitted until you approve it. Share access with /link invite.

When something looks wrong, ask. Every line of doctor is measured at the moment you run it — a live socket, a real port probe, the negotiated TLS version — never a stored assumption.

Topology

How it fits together

One terminal hosts a room on port 9900. Every other terminal joins it as a client. That is the whole topology: a star, not a mesh — and it says so, because the hub terminates TLS and reads everything it routes.

What "connected" means

Exactly one thing: authenticated and admitted. A socket that is open but not yet approved reports Pairing, never Connected. Discovery finding a hub is not a connection, and it is never trust.

Model

Four identities

Every question about who may do what resolves to one of these four.

IdentityWhat it isLifetimeLives in
DeviceSHA-256 of the certificate's SPKI: ed25519-sha256:5C:4E:…Permanent, per machine~/.omp/identity/
Agent instanceOne running terminal; a random uuid at startupThe processmemory only
WorkspaceA canonical repository root a peer may inspectWhile registeredmemory + per-device allow-list
RoomOpaque id bound to the hosting device's principalUntil you leave it~/.omp/link.json
Why a room is not a name

If two machines both create a room called backend, those are two different rooms that share a label. A room is the pair (roomId, hub principalId), so "same name" can never silently mean "same room", and a host whose key changed can never inherit a room you already trusted.

Three terminals on one laptop are three agents — not three devices, and not one recipient. That is why an execution grant issued to one terminal is unusable by the terminal beside it: grants key on (device, agent instance).

Current limitation

Nested repositories share the parent's export: a terminal registers its cwd as the default workspace. If ~/dev/api contains an inner repo, an inspect-capable peer sees through to it. Named workspace exports are the next piece of work.

Scenario B

Two machines on a LAN

A different machine is a different identity, so it is verified once, forever. Four words, compared by a human on two screens. The words are never transmitted: both sides derive them independently from the TLS session, so a match proves you share one channel and nobody sits in the middle.

Across a Tailnet

Without Tailscale

Everything works on a plain LAN with no extra software; the only difference is reach. Same subnet, use the LAN address. Different networks, Tailscale is the transport that makes the machines adjacent. The trust model is unchanged either way.

Beyond Pi

From Claude Code, Codex and other MCP hosts

omp-link-mcp is a stdio MCP server: newline-delimited JSON-RPC 2.0 on stdin/stdout, hand-rolled, no new dependency and no build step. A host that speaks MCP — Claude Code, Codex CLI, Cursor — joins the same room as a Pi terminal, pairs the same way, and is bound by the same capabilities and the same audit log.

It appears as its own terminal, named <name>-mcp, because it is one. The Pi terminal and the MCP server on a single machine share a device certificate but are two agents, and a peer aiming link_send at a name has to know which of them it reached.

Claude Code

shellomp-link on PATH
claude mcp add --transport stdio omp-link -- omp-link-mcp

Add --scope project to write .mcp.json into the repo instead of your user config. From a git checkout, point at the launcher itself:

shellfrom a checkout
claude mcp add --transport stdio omp-link -- node /absolute/path/to/omp-link/bin/omp-link-mcp.mjs
.mcp.jsonproject scope, by hand
{"mcpServers":{"omp-link":{"command":"omp-link-mcp","args":[]}}}

Confirm it registered with claude mcp get omp-link, or /mcp inside the session.

Three things that bite

The -- is mandatory: everything after it is passed to the server untouched.

Do not add a type field. An entry without one is read as stdio, which is what this server speaks.

A project-scoped .mcp.json server sits at Pending approval until the workspace is trusted — and a cloned repo cannot approve its own servers.

Codex CLI

shell
codex mcp add omp-link -- omp-link-mcp
~/.codex/config.tomlthe same registration, by hand
[mcp_servers.omp-link]
command = "omp-link-mcp"
args = []
cwd = "/Users/you/dev/api"

[mcp_servers.omp-link.env]
OMP_DIR = "/Users/you/.omp"

The table name is mcp_servers — snake_case and plural. cwd and env are optional, and cwd is load-bearing: it becomes the node's workspaceRoot, which is exactly what a peer's link_exec inspects. Confirm with codex mcp list, or /mcp inside the session.

Six tools, not seven

The Pi set minus one. link_status does one extra job here: it delivers messages that arrived while no tool was running. MCP gives a server no way to push them, so they wait and are cleared once reported.

link_compact is deliberately absent. Compaction only means anything where the host exposes a compaction API for the agent's own context — Pi does, MCP has no such primitive. Exposing it here would answer "compacted successfully" without compacting anything, and a tool that silently does nothing is worse than an absent one.

What the server will not do by itself

It attaches to the room already recorded in link.json. It never creates a room, never pairs on its own and never opens a listening port: a background process started by an editor must not put a TLS server on your LAN because a config file remembers a room. Creating and joining stay human decisions — omp-link create <name>, omp-link join <ip:port> or /link. If a room appears while the server is running, the next tool call attaches to it.

It also never serves shell execution. --unsafe-remote-exec is a per-launch decision made at a terminal you are watching; peers can still ask it for structured inspection, gated by the same capabilities as anywhere else.

Runs under bare node: Node 22.18+ strips types itself, a checkout that has run npm install uses tsx, and Node 22.6–22.17 is re-executed with --experimental-strip-types. tools/list answers even when the link is down, so a host can build its tool catalogue before you have a room.

Lifecycle

When the host leaves

The obvious failure of a peer-hosted design: close the hosting terminal and the room dies. omp-link avoids it without a background service, using something already true — terminals on one machine share a device certificate.

When the hosting terminal exits, a surviving local terminal claims port 9900 and presents the certificate remote peers already pinned. Their pins stay valid. Nobody re-pairs.

An exit that closes its sockets is seen at once. A host that freezes — suspended, lid shut, network gone — closes nothing, so the survivors wait out the silence timeout first: succession is immediate on a clean exit and takes up to a minute on a wedged one.

~/dev/web — the survivor
(the terminal in ~/dev/api was closed)

The terminal hosting "backend" exited. This terminal is now hosting
the room; peers keep the same pinned identity and reconnect automatically.

audit.log: local_hub_succession

There is no --keep flag and no service to install, because there is nothing for you to decide. If a local terminal survives, the room survives. An explicit /link off never triggers a takeover of the port you just released.

How a dead peer is actually noticed

A suspended process, a closed laptop lid or a dropped Wi-Fi link leaves an established socket that neither end notices for minutes — a SIGSTOPped peer still ACKs at the TCP layer. Only an unanswered WebSocket ping tells the two apart, so each side pings every heartbeatIntervalMs and counts any inbound traffic — a pong, or any frame at all — as proof of life.

Hub watching a peerClient watching the hub
Pings everyheartbeatIntervalMs — 15s
Silence tolerated30s: interval × heartbeatMissesBeforeDrop (2)45s: clientHubSilenceTimeoutMs
Noticed within45s worst case — silence is judged on the next tick60s worst case
Thenclosed 4408, grants revoked, transfers cleaned, roster rebroadcast, peer_liveness_timeout auditedthe agent goes disconnected, and that transition is what triggers local succession

So the roster is bounded-stale, not live: a peer that vanished without a close frame is still named for up to 45 seconds and no longer. A terminal that comes back — after a crash, a sleep, a network flap — presents the same agentInstanceId and evicts its own previous connection (peer_connection_superseded, close 4409) rather than appearing in the room twice.

The asymmetry is deliberate. The client's deadline is the longer one because a client that declares its hub dead too eagerly starts a takeover of a port that is still being served, and a spurious succession is worse than a slightly stale roster. Every number here is a key in link.json; none of them is compiled in.

Honest limit

Succession is local only. If the last terminal on the hosting machine exits, the room ends. Remote peers notice within their silence timeout and keep their pin, but nothing re-dials for them: there is still no reconnect backoff, so they rejoin with /link on once a host is back. Hosting never migrates between machines — that is a different device identity, and every pin would rightly reject it.

Treat peer output as data

Messages, filenames and inspection results from a peer are untrusted input. A trusted device is not a trusted instruction source: never let a peer's text act as a system directive.

Configuration

One file — ~/.omp/link.json, written at 0600 — holds the rooms this machine remembers and every timeout it uses. Tunables that used to be constants scattered across four modules are config keys now, so the heartbeat, the pairing window and the RPC deadline are settings rather than rebuilds.

~/.omp/link.jsontimings override per key
{
  "configVersion": 1,
  "terminalName": "mac-studio",
  "network": "lan",
  "currentRoomId": "8f2c1d4a-…",
  "rooms": [],
  "timings": {
    "heartbeatIntervalMs": 20000,
    "rpcTimeoutMs": 45000
  }
}
KeyDefaultBounds
handshakeTimeoutMs10sTLS connected to authenticated or paired; exceeding it closes 4408
pairingWindowMs60sHow long a pairing request waits for a human to compare four words
heartbeatIntervalMs15sInterval between liveness pings on an authenticated connection
heartbeatMissesBeforeDrop2Silent intervals tolerated before a peer is dropped — a count, not milliseconds
clientHubSilenceTimeoutMs45sSilence from the hub that means, to a client, that the hub is gone
rpcTimeoutMs30sHow long link_exec waits for its correlated response
transferInactivityMs30sNo chunk for this long fails an in-flight transfer
transferAbsoluteMs120sCeiling on one transfer regardless of progress
discoveryProbeMs1.2sBudget for one discovery sweep: loopback, UDP broadcast, tailscale
grantDefaultMs10minLifetime of an execution grant when the approver does not set one

Every value is validated per key against a floor, so a typo degrades to "slow", never to "unusable", and one bad key never poisons its neighbour. Loading never throws: a truncated, empty or hand-mangled file yields defaults plus a warning that doctor prints on the config problem line. Keys this build does not know are written back untouched, and a file from before v3.4.0 — one with no configVersion — is migrated forward silently, because a room list is not an authorization decision.

What is deliberately not configurable

Protocol and safety limits — chunk size, maximum file size, dedupe cache, rate-limit windows, roster cap — are not keys. They are part of the wire contract or the security model, and a config file must not be able to widen them. Timings are read once when a terminal starts, so an edit takes effect on the next start, not mid-session.

Boundaries

What it does not do

Stated plainly, because a security tool that oversells itself is worse than none.
